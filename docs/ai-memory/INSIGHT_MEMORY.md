## 0. 記憶の読み方と情報の優先順位

1. **ユーザーが現在明示した指示・承認・変更禁止範囲を最優先**する。
2. 現在の実装状態・公開状態・SHAは、必ず作業開始時にGitHubの**最新 `main`** を取得して確認する（本ファイル記載のSHAは最終確認時の記録にすぎない）。
3. 本ファイルの「確定仕様」はユーザーの要求・合意事項として扱う。**実装済み**とは限らない。コードと違うときは「要求仕様と実装との差」として報告する。
4. 「将来構想」「提案」「保留」は、承認済みの実装指示として扱わない。
5. 確認不能な情報を事実として補完しない。実装・公開・記憶ファイル更新は、対象範囲と承認を確認して実施する。

## 3. 既存の主要仕様・設計方針【合意事項】

### 3.1 ダッシュボード

- KPI表示は売上、客数、廃棄金額を中心とする。前年比を見やすくする。不要な補助説明は減らす。
- 年間サマリーから買上点数を除外し、残った項目を見やすく再配置する。
- 基準年と比較年を選択できる。ダッシュボードの1〜12月選択ボタンは選択月が明確に分かるようにする。
- 年度の追加・削除は**設定ページの「年度管理」**に配置。操作ボタンは「＋ 追加」「− 削除」。削除時の確認手順とデータ保護を維持。
- ページ移動時にユーザーの選択月・分析対象の意図しないリセットを避ける。

### 3.2 販売数・納品数

- カテゴリー単位で日別に管理し、**1日1〜3便**の納品数と販売数を入力する。対象外便は「ー」で表しグレー化。
- カテゴリーは追加・削除等の管理を行い、店舗間の共通マスターとして扱う箇所がある。
- 未入力は集計から除外し、明示的な **0** は実績値として含める。1日合計は対象となる全便の入力済みデータのみ平均対象にする。
- **平日平均 = 月〜金、祝日を除外**。土曜日は含めない。
- **日曜日・祝日平均 = 日曜または祝日**。対象店舗・月・カテゴリーで集計し、セール・イベント対象日は除外する。
- 販売入力ページに集計を重複表示しすぎず、セール実績は専用ページに集約する。

### 3.3 天気・気温

- 過去の天気・気温データを実績と紐付け、気温は整数表示（小数切り捨て）。
- 過去4日より前の取得ではHistorical Forecast APIを利用する仕様を採用。
- 同じ市区町村の店舗では気温を同期する方針。
- 将来日の**天気予報表示**は「発注予測」ページで実装・公開済み。天気・気温の予報表示と、未実装のAIによる需要数値予測は区別する。気象情報を外部取得する場合も、店舗の実績データを外部AIサービスへ送信しない方針を維持する。

### 3.4 イベント・催事・セール

- 店舗イベントと近隣イベント、店舗別・全店共通イベントを区別して管理する。
- 単日開催と複数日開催で表示内容を切り替え、売上・客数の合計と1日平均が単日に重複しないようにする。
- 単日は「カテゴリー実績」、複数日は「開催期間のカテゴリー実績」を表示する。複数日では日付別の売上・客数カードを開催期間カテゴリー実績の上に配置する。
- 時間帯別客数の棒グラフは元の青い細めのデザインを保つ。普段は数字を常時表示せず、タップ時に人数を表示する。
- イベント・催事に紐付く任意の「特需商品」を登録できる。カテゴリー別の実績表示を行う。
- 特需商品の「よく使うカテゴリー」は**全店共通の独立マスター**で、販売数入力のカテゴリーマスターとは別に扱う。追加・編集・削除・並び替え、自由入力からのお気に入り登録が可能な仕様。
- 7日分並ぶカードの幅を基準にした、11インチiPadでのレイアウトの安定性を重視する。
- セールのよく使う設定、セール実績専用ページ、便別の納品・販売実績の確認を維持する。

### 3.5 現行の分析AI（既存機能）

- ダッシュボード・売上・廃棄などの分析コメントを表示する機能がある。
- 操作入口はサイドバーの「分析AI」。ウィンドウの閉じるボタンおよびサイドバーから開閉できる。
- 分析対象の期間やページ選択を維持し、ユーザーにとって重要な数値と要点を優先する。
- コメントは数値の単なる言い換えより、意味・注意点・改善提案を重視する。
- **分析AI開閉アニメーション【修正・実機確認済み】**: 2026年10月に発生した、iPadで分析AIを開く際にアニメーションが瞬間的になる問題はPR #182で修正済み。ユーザーによる全ページの実機確認も完了。既存の表示位置・余白・アニメーションを維持し、今後の修正では再発を防止する。

### 3.6 発注予測【実装・公開・実機確認済み】

- サイドバーの「発注予測」は、**天気予報と過去の納品・販売実績**を同じページで確認する閲覧専用機能。現段階では**AIによる需要数値予測は未実装**。既存のダッシュボードと区別する。
- 発注締切は日本時間**11:00**。標準の納品日は**11:00前なら翌日、11:00以降なら翌々日**。ユーザーが明示選択した納品日は自動変更しない。
- 選択納品日を7日間表示の**左から4列目**に配置する。
- 前年比較は**364日前（52週前）**を基準とし、天気予報と前年実績を**曜日で揃える**。
- 過去日の天気・気温は**店舗の保存済み実績**を使用する。保存がなければ「実績未登録」と表示し、天気予報で過去実績を補完・推測しない。
- 発注予測ページは**閲覧専用**で、既存の保存データを書き換えない。

## 4. Insightの次世代AI構想【ユーザーが明示した目的・未実装】

**最重要目的**: 過去の実績を総括するだけでなく、**納品予定日の需要を予測して発注判断を支援する**。

### 4.1 ユーザーがAIに求める4機能【要求事項】

1. **データの読み取りと傾向把握**: 客数・販売数・天気・気温・曜日の実績を使い、増減や関連性を分析する。
2. **データの総括**: 現在の「分析AI」を発展させ、売上・客数・販売数・廃棄などの状況、理由、改善点を説明する。
3. **納品予定日の販売数を予測**: 過去の客数・販売数と、対象日の天気予報・予想気温・曜日を用いて、需要と発注の判断材料を算出する。
4. **能動的な警告**: 天気予報・曜日・祝日等を考慮し、客数や販売数が増えそう／減りそうな場合に警告し、発注調整を支援する。

### 4.2 検討中の技術的な実装方針【提案・未確定】

- **数値予測は統計モデル／機械学習で担当**し、**分析結果の解説を小型ローカルLLMで担当**する構成を第一候補とする。LLMの文章生成だけで発注数を決めない。
- まず**カテゴリー別・便別の予想販売数**を予測する。商品ごとの予測には商品別実績が追加で必要。
- 予想販売数と**最終発注数は区別**する。発注数まで算出する場合は、在庫数・欠品情報・発注締切・納品時刻などを考慮する必要がある。
- 平日／土曜／日祝、祝日や連休、季節性、イベント・セールを適切に区別する。
- AIの予測と実績の誤差を蓄積・評価し、根拠・サンプル件数・不確実性が分かる形で提示する。「警告」は根拠と推奨アクションを簡潔に併記する。
- ローカル処理優先。**店舗実績や機密情報を外部AIサービスへ送信しない**。気象予報の外部取得は許容する方向だが、通信仕様・許可範囲は実装前に確認する。
- InsightはブラウザベースのWebアプリ。Apple Intelligence／Apple Foundation Models APIをWebから自由に直接利用できると仮定しない。Web内のモデル実行とネイティブ連携を比較検討する。
- 検討中の端末はM5 iPad Pro 11インチ。**256GBか512GBかは未決定**。256/512GBは計算性能が基本的に同等で、選択の主な違いは保存容量の余裕。ストレージ購入判断をLLM規模・実装方式の検証より先に確定しない。

### 4.3 おすすめする開発順序【提案・未着手】

- **STEP 1**: 過去データの傾向分析（曜日・天気・気温と客数／販売数）。
- **STEP 2**: 納品予定日のカテゴリー別・便別需要予測。過去実績と予測の誤差検証。
- **STEP 3**: 在庫・納品条件を考慮した発注支援、需要変動の警告。
- **STEP 4（必要なら）**: ローカルLLMによる自然言語の解説を統合。

> **誤認防止**: 上記の将来AI機能は「要件・構想」であり、2026-10-09時点で需要予測や自律的な発注最適化の実装完了を確認したものではない。

## 5. ChatGPT自身の外部記憶プロジェクト【GitHub原本運用】

- **目的**: 新しいChatGPTチャットでも、Insightの設計判断・仕様・進捗を長期間正確に引き継ぐ。
- **原本（Single Source of Truth）**: GitHub `Kazutake1/Insight` の `main` にある **`docs/ai-memory/INSIGHT_MEMORY.md`** を採用する。変更履歴はGitHubのコミット／PRで管理する。
- **ChatGPTプロジェクトの登録済みファイル**: 初版のコピー（読み取り用の予備資料）として利用する。**GitHub側を更新してもChatGPTプロジェクトの添付ファイルは自動更新されない**。情報が違う場合、まずGitHubの最新 `main` にある原本を確認する。
- **読み取り手順**: 重要な仕様や過去の決定を参照するときは、GitHubの最新 `main` と本ファイルを取得する。GitHubにアクセスできない場合、手元の登録済みファイルを参照し、最新版でない可能性を明示する。
- **更新手順**: ユーザーが「記憶を更新して」などと依頼したら、まず最新原本を読み、既存の記述と照合して**追加・変更・削除の案**を提示する。ユーザーがその更新内容を承認してから、専用ブランチ→記憶ファイルのみ変更→PR→確認→main反映の順に進める。指示のない自動書き換えはしない。
- **境界**: 記憶ファイルの更新はInsight本体の実装・テスト・公開反映を意味しない。コードやデータ変更は別途明示的な依頼が必要。PRがmainへ反映されるまでは「更新完了」としない。
- 記憶更新は「確定仕様」「実装済み」「検証済み」「未実装」「保留」の状態を必ず区別する。
- ChatGPTの標準メモリだけに依存しない。必要時は「GitHubの最新版INSIGHT_MEMORY.mdを参照して」と依頼する。
- **セキュリティ**: このリポジトリは公開される前提。実売上・従業員情報・パスワード・APIキー・その他の機密情報を本ファイルへ記載しない。

## 8. 更新を簡単にする短い依頼文【運用ルール】

| ユーザーの依頼 | 実施すること |
|---|---|
| 「記憶を確認して」 | GitHub最新 `main` の記憶ファイルを取得し、該当内容を答える。変更しない |
| 「記憶の更新案を作って」 | 現在の会話・最新実装と原本との差分を提示する。変更しない |
| 「この内容で記憶を更新して」 | 直前に承認された差分のみを記憶原本へPR経由で反映・確認する |
| 「記憶と実装を照合して」 | 最新のGitHubコードと記憶の差を調査・報告する。変更しない |

- 上記は専用コマンド機能ではなく、**会話の中で使う依頼文**。どのチャットでも実行するには、必要なGitHub接続・権限が利用できる必要がある。
- 変更箇所だけ編集し、既存の他の記述は維持する。変更後には更新対象・PR・main SHA・未反映事項を報告する。

## 9. Work実装・テスト・公開の共通手順【確定・2026-10-20承認】

この節は、ユーザーが**Insight本体の実装・修正と反映を明示的に依頼した場合**に適用する。毎回のWork向けプロンプトには変更対象と今回固有の条件だけを書き、下記共通手順は本ファイルを参照する。現時点のユーザー指示・承認範囲を最優先する。

1. **作業開始**: GitHubの最新 `main` と本ファイルの原本を取得し、関連コード、既存仕様、完了済み作業、影響範囲を確認する。
2. **変更範囲と保護**: 指定外の変更や既存デザインの意図しない変更をしない。保存済みデータ、店舗別・共通マスター、過去の履歴、保存形式、`insight_v11` を保護する。
3. **検証**: 変更に対応する単体・構造・回帰テストを実施し、Chromium／WebKit E2Eと、必要な場合は11インチiPad横向きのライト／ダーク・表示崩れ・操作を確認する。実機未確認は未確認と報告する。
4. **セキュリティ**: `.env`、APIキー、トークン等を公開領域に含めない。デプロイ前に公開ファイルを検査する。APIキーを使う場合は権限制限と利用額アラートを確認し、設定を確認・実施できない場合は未確認事項として報告する。
5. **GitHub反映**: 専用ブランチとPRで変更し、必要なCI・回帰テスト・セキュリティチェックがすべて成功したことを確認してから `main` へマージする。コード公開を伴う場合はGitHub Pagesの公開結果を確認する。
6. **完了報告**: 変更内容、テスト結果、PR番号・URL、最新 `main` SHA、公開・反映状況、残る未確認事項を簡潔に区別して報告する。

**適用上の区別**: 調査・相談・報告だけの依頼ではコード変更、コミット、PR、公開を行わない。外部記憶の更新は第5節・第8節の事前承認ルールに従い、Insight本体のコード変更・公開と区別する。

## 10. 利用枠節約・重複作業防止【確定・2026-10-29承認】

ChatGPTとAI社員Work（Work/Codex）の利用枠を節約し、**不要な確認・再実行・作業の重複を避ける**。ただし、安全性に必要な検証や独立レビューは省略しない。

1. **完了済み作業は繰り返さない**: 作業開始時にIssue #211などの既存記録と対象PRを確認し、完了済みレビュー・テスト・調査は原則として再実施しない。新しい変更・未確認事項がある場合のみ必要な差分を対象にする。
2. **GitHub確認の回数を抑える**: 最新 `main`、関連PR、CIの状態を可能な範囲でまとめて確認する。CI実行中の短い間隔での繰り返し照会を避け、開始・失敗・完了など必要な節目で確認する。
3. **テストの重複実行を防ぐ**: 同一HEADで成功済みの検証結果は再利用する。失敗時は原因を特定し、必要な対象・ジョブのみを再検証する。コード変更でHEADが変わった場合は、その新HEADに必要な正式CIを実施する。
4. **ChatとWorkの分担を明確にする**: Insight Chat側は実装・検証・完了判定、AI社員Work側は独立レビューを担当する。同じ調査を両者で理由なく繰り返さず、Issue #211で結果・差分・次の担当を共有する。
5. **過度に細分化しない**: 同じ担当が連続して実行できる作業は、合理的な範囲でまとめて進める。小分けにすることで利用枠や往復回数を不必要に増やさない。ただし、変更範囲の限定、データ保護、必須CI、独立検証は維持する。

**運用上の注意**: 進捗確認のための頻繁なCI照会は避ける。未完了のテストやレビューは未完了と明示し、結果を推測で成功扱いしない。

## 11. チャット上限対策・コンテキスト容量節約【確定・2026-10-29承認】

開発チャットが短期間で会話上限に達することを抑えるため、**GitHubから取得する情報量・回答量・引き継ぎ量を必要最小限にする**。第10章の重複作業防止ルールと併用する。安全性・正確性に必要な確認や検証まで省略しない。

1. **GitHubの取得量を最小化する**: Issue #211の全コメントや過去の全PR、長大なコード全文を毎回取得しない。最新の関連コメント、対象PRのメタ情報、変更差分、必要なファイル・行だけを優先して取得する。全文取得が必要な場合は理由と対象を限定する。取得した長文をそのまま会話へ再掲しない。
2. **確認・再実行の反復を避ける**: 既に確認済みの事実、同一HEADで成功済みのCI、独立レビュー、テスト結果を再利用する。新しいHEADや未検証の変更、失敗などがある場合のみ、必要な差分・検証対象を特定する。ユーザーの「次」には、未完了工程だけを進める。
3. **通常の作業報告を短くする**: 原則として「実施内容・結果・次の作業・次の担当」の4項目を簡潔に報告する。技術的な詳細が必要な場合はIssue #211の該当記録へ集約・参照し、同じ長文をチャットへ繰り返し掲載しない。重大な不具合・データ保護上の危険・未確認事項は省略せず明示する。
4. **チャット間の引き継ぎを簡潔にする**: GitHub最新 `main` の本ファイルとIssue #211の必要な最新記録を基準にし、引き継ぎ文は原則300〜500文字程度とする。過去の開発履歴を毎回全文読み直したり貼り直したりしない。参考SHAは必ず最新状態と区別し、完了・未完了・次担当を明示する。

**限界**: これらは会話内で処理する情報を減らすための運用ルールであり、ChatGPT自体の利用上限やコンテキスト制限を変更するものではない。GitHub原本・Issueへの記録にも実店舗データや秘密情報を含めない。
