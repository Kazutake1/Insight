# IndexedDBの保存停止後に確認する内容

Draft #341の隔離環境で、診断は保存停止中の採用記録、IndexedDBのレコード、移行元の `insight_v11` を読み取る。保存停止中に診断を繰り返すことができる。

| 診断結果 | 照合できた内容 | 手動復旧画面での扱い |
| --- | --- | --- |
| 移行コピーを確認 | 移行時の識別子、初版の原文、現在の移行元が一致 | コピーを確認した時点と移行元を表示する |
| 保存を確認 | 操作ID、版番号、候補と直前版のダイジェストが一致 | 現在版と直前版を区別して表示する |
| 保存前の版を確認 | 現在版が中断した操作の開始時点と一致 | 保存前の版が残っていることを示す |
| 照合不能、記録欠落、診断中の変更 | コピーまたは保存結果を確定できない | 保存停止を継続し、既存の暗号化バックアップの確認に案内する |
| 試行履歴のみ残存 | 移行試行IDは残っているが、主DBと採用記録が存在しない | 初回移行として再実行せず、暗号化バックアップの保全と手動確認を案内する |
| 試行履歴欠落・不一致 | 採用記録のIDと別DBの試行記録が照合できない | 新たな保存を停止し、原因調査とバックアップ確認を要求する |

再開操作を接続する際は、本人が保持する内容と暗号化バックアップを確認し、再開を明示的に選択する。選択後に排他ロックを取得し、確認時の採用記録、移行元原文、版番号、現在版と直前版を再照合する。確認後に変更を検出した場合は保存停止を継続する。旧版タブや旧PWAとの競合を制御できる状態を、公開前に別途検証する。

このDraftは候補の表示、確認の取消、確認後の再照合までを試験する。各結果で採用記録とデータを保持し、保存停止を維持する。

移行試行IDだけを記録した直後にアプリが中断した場合も、再起動後の読み取り診断は `history-only` として保存停止を表示する。採用記録が有効でも履歴DBが消失・不一致なら `history-missing` / `history-mismatch` として新たな保存を拒否する。履歴を削除して自動的に移行し直す処理や、確認だけで書き込みを再開する処理は設けない。

## 復旧画面の案

最初に保存停止を表示し、確認できた現在版・直前版の版番号と、対象の店舗・年度を表示する。「暗号化バックアップを確認」「閉じる」を用意し、確認できる版が一つに定まった場合だけ「この版で保存を再開」を提示する。選択時に表示した版の識別子・各原文・採用記録を照合し直す。旧版タブやPWAと同時実行できる間は、診断までを提供する。初回移行の確認後、コピーより先に別のIndexedDBへ試行IDを記録する。主DBと採用記録を失っても試行記録が残っていれば初回扱いを拒否する。サイトデータ全体が消え、試行記録まで失われた場合はブラウザー内で履歴を確定できない。本番導線では暗号化バックアップに基づく本人判断が必要となる。

## 移行前に確認する操作

| 操作 | Draftでの検知 |
| --- | --- |
| 今日の入力、売上・客数・廃棄、販売数入力 | 画面の未保存状態と保存済み原文を比較 |
| イベント、カテゴリー、店舗・年度、廃棄予算 | 開いているダイアログ、店舗メニュー、年度追加欄を検知 |
| CSV取込、天気・気温取得、天気地点検索、過去の天気の一括取得 | 読み込みや取得の終了まで待つ |
| 暗号化バックアップ、復元 | 実行中と復元後の保存停止を検知 |

設定画面や今後追加する操作について、ダイアログを使わず未保存値を保持する経路と、画面遷移後も続く処理は、各保存入口をIndexedDBへ接続するときに個別に照合する。

## 本体接続の順序と保存時の注意点

| 優先 | 保存入口 | 保存先を接続する際の検証 |
| --- | --- | --- |
| 1 | 起動、店舗切替、バックアップ・復元、生データ保全 | 採用状態・版番号の読戻し、暗号化ファイルの互換性、復元中の別タブ競合と操作停止 |
| 1 | 今日の入力、売上・客数・廃棄、時間帯客数、販売数とカテゴリー | 本体・メモ・気温・共通天気など、同じ操作から続く書込みを一度に確定。入力を消す前に確定結果を検証 |
| 1 | 店舗と年度の追加・削除、日／月のクリア、CSV | 選択中の店舗・年度と対象版を明示。店舗削除と次の店舗選択を一括確定し、CSV読込後にも対象を再確認 |
| 2 | 店舗・近隣イベント、催事・セール、共有テンプレート | ダイアログの入力を維持し、店舗単位と全店舗共通の更新を区別 |
| 2 | 天気・気温、地点の設定と解除、過去天気補完 | 取得後に対象店舗、対象日、版番号を再確認し、進行中や一部確定時の操作を検証 |
| 2 | 廃棄予算、店舗の設定、テーマ、ブラウザー側の表示設定 | スナップショットに含まれる店舗設定と独立した表示設定を分け、既存値の維持と確定後の反映を確認 |

各入口の非同期接続と実機検証は後続工程。今回の試作は保存停止中の確認に限定する。

試行履歴だけが残る場合の試作では、利用者が選んだ暗号化バックアップを復号し、店舗・年度の情報と移行元データ全体を照合する。本人の確認後に試行ID、移行元原文、主DBと採用記録の状態を再確認する。対象は照合までで、保存停止を維持する。公開画面への接続と、履歴も消失した場合の画面は後続工程。

主DB・採用マーカー・試行履歴DBと `insight_v11` がすべて見つからない場合は、履歴不明として保存を停止します。初めて使う端末とサイトデータ消失後の端末をブラウザー内の記録だけで区別できないためです。隔離試作では選択した暗号化バックアップの復号と既存の復元前検査を行い、作成日時、店舗、年度を確認できます。確認の前後で保存状態を再診断し、途中でデータや記録が現れたときは照合を中止します。確認結果は保存停止のままです。隔離用の確認画面でファイル選択、パスワード入力、概要表示、取消を試験します。通常起動への接続と、本人が復元を実行する操作は後続工程です。

旧形式の `insight_v9` または `insight_v8` が残る場合は、履歴不明の空の状態と区別し、この照合処理を開始しません。確認中に旧形式データが現れた場合も処理を中断します。通常起動への接続は現行の旧形式読み込みを維持し、初期データの生成より前に診断できるようにします。

起動前の試験では `diagnoseStartup()` を初期店舗の生成より前に呼びます。採用マーカーも両方のDBも存在しないことが確認でき、現行または旧形式の保存キーがある場合に限り、従来の読み込みへ進める状態を返します。データ本体の検証は従来の読み込み処理が担当します。IndexedDB採用済み、保存履歴不明、診断中の排他取得失敗などは停止を返します。この判定は通常ローダーに未接続です。別タブを用いた試験では他タブの保存原文とマーカーが残ることを確認します。

Draftの共通保存処理は、採用マーカーがある間、または開いているタブが採用マーカーを一度でも観測した後は、旧保存先への書き込みを停止します。採用マーカーの内容が壊れている場合も保留します。通常の保存、共通保存処理を使う復元、トランザクションを対象とします。この変更を含まない過去のアプリやPWAが直接書き込む場合の防止策は後続です。

IndexedDB採用後も旧版タブが旧保存先に直接書き込めるため、IndexedDBの読込・保存時に移行元の原文との差を検知したら、採用マーカーに `source-conflict` を記録して停止します。旧保存先とIndexedDBの既存レコードは保持し、旧保存先の原文が元に戻った後も自動再開しません。旧版からの書き込み自体や、確認の間に書き換えと元戻しが完了した場合を阻止・検出する仕組みではありません。公開前には旧版タブ・PWAの利用停止と、更新後の再起動・競合の実機確認が必要です。

### 旧版を停止してから移行するための確認

移行前に利用者が旧版のタブとホーム画面から開く旧アプリを閉じ、更新後のInsightを開き直します。Draftの確認処理は、この申告に加えて、起動中のビルド・機能一覧が移行用の版と一致し、ネットワークから取得した起動ページでも同じビルドを確認でき、Service Workerの登録や制御がない場合だけ準備済みと返します。通信できない、版が違う、Service Workerの状態を確認できない、照合中に登録が現れる場合は停止します。

この確認では閉じたアプリの一覧を取得できません。利用者による確認は旧版が実際に停止したことの技術的証明ではなく、移行元の原文照合も引き続き必要です。自動試験では、バックアップ確認中に実際のService Workerが登録されてページを制御し始めると、採用記録を作成せずに中止することを確認します。続けて、旧版を模したページがキャッシュから開き、移行元の原文が残ることを確認します。Chromiumでは通信を切断します。WebKitのCIでは通信切断を模擬すると内部エラーになるため、配信元にページがない状態でキャッシュからの再起動を確認します。今回の工程ではiPad実機テストを省略し、ホーム画面からの起動は未確認です。旧版からの書き込みを防げること、または競合時に双方のデータを保持して安全に停止・復旧できることを確認するまで、公開の移行操作は有効にしません。

隔離試験用の `migrate()` は、旧版を閉じたことの明示確認が必要です。移行用として固定したビルドと機能一覧を使い、排他ロック下でバックアップ作成前と確認後に環境を照合します。バックアップ確認後に保存先・移行履歴・旧保存の原文を再確認し、変化を認めた時点で移行を中止します。隔離画面では実際のシェルローダーを呼ぶ前に保存状態を診断します。旧保存データがあるときはシェルを起動し、`insight_v11` がある場合は旧版を閉じたことを確認してから移行ボタンを押せます。暗号化ファイルの保存確認を取り消すとシェルに戻り、もう一度操作するには旧版終了の再確認が必要です。コピー後は隔離画面を再読み込みし、保存停止を表示して旧シェルを起動しません。公開ローダーへの接続、IndexedDBでの通常保存、手動での保存再開は後続工程です。

移行後に旧版のページをキャッシュから開いて旧保存先に書き込む自動試験も実施します。新しい画面は起動時に旧シェルを開かず、IndexedDBの読み取りで旧保存先との不一致を検出した後は、保存と既存の復旧確認を停止します。旧保存先に残った編集、IndexedDBに確定済みの版、その直前の版をそれぞれ照合します。Chromiumは通信遮断下で試験し、WebKitは配信元にページがない条件で試験します。WebKitでの完全な通信遮断は未検証です。

## 「今日の入力」の隔離試験設計

「保存する」から呼ばれる同期の `saveQuick()` は、選択日の属する年度を必要に応じて作り、売上・客数・買上点数・廃棄内訳と合計・天気を更新します。共有天気と、同じ日の行を持つ全店舗の天気も更新します。その後、同期フックが店舗メモを対象行に保存し、最高・最低気温の更新または消去と、同じ市町村で同じ日の登録行を持つ他店舗への天気・気温の反映を行います。各段階で個別に旧保存先へ書き込むため、最後の書込みだけを差し替えると途中状態が残ります。現状の保存表示は本体側で後続フックより先に出ます。

初回の隔離試験は、登録済み年度の当日または過去日の「保存する」1操作を対象にします。実操作の入口で店舗ID・選択日・年度・月・確定版を固定し、既存の数値変換と気温検証の結果から、選択行と共有先への変更を候補スナップショットにまとめます。同期の本体処理と後続の書込みフックは実行させず、版を指定して候補を一括確定します。保存結果を読み戻して、店舗・日付・入力・対象版の一致を確認してから画面と保存表示を更新します。取消・入力不備は書込み前に止め、競合や結果不明では入力を表示したまま追加保存を止めます。

架空2店舗・複数年度を使い、同一市町村と異なる市町村の条件を切り替えます。店舗の売上・客数・買上点数・廃棄・メモの更新範囲、共有天気と気温の反映先、別日・別年度・他の項目と旧保存原文の保持を、保存結果全体の比較で確かめます。保存中の日付・店舗変更、気温の不正入力、保存競合・容量不足、読戻し中断も検証します。年度自動作成、未来日、自動取得、クリア、通常起動および手動復旧への接続は後続工程です。

隔離実装の `InsightIndexedDBQuickInputPreviewV1.connect()` は、採用済みIndexedDBと画面の元データが一致する「今日の入力」だけで動作します。「保存する」の既存入口で入力を採取してから同期処理を止め、既存の保存監視で非同期の完了を追跡します。読戻し後に入力・店舗・日付を再照合し、成功時だけ確定済みデータと未保存状態を更新します。処理中・停止中は日付移動を拒否し、通常時の日付移動には既存の未保存確認を使います。店舗切替、クリア、天気自動取得および他画面への移動は隔離中は停止します。通常ローダーからは読み込みません。

隔離中の未保存判定は、対象日を最初に表示した時点または保存確定時の入力値と、現在の全保存項目を比較します。コンパクト天気選択やフォームの外側にある気温欄も比較対象です。日付移動とページ離脱は同じ判定を使います。読み取れない入力がある場合は未保存として扱い、日付移動を取り消した場合は元の入力を保持します。

「今日の入力」と売上・客数・廃棄をつなぐ隔離試験は、今日の入力で開始し、4画面で一つの確定版・保存待ち・保存停止の状態を共有します。画面移動の確認は現在の画面の下書きだけを判定し、取り消した場合は表示・入力を保持します。同意した移動先は確定済みデータから描画します。月次画面では表示対象の店舗・年度・月を照合し、今日の入力に戻ると表示日の未保存判定を作り直します。保存受付から確定版の読戻しまで、別画面への移動・追加保存・店舗切替を停止します。

店舗切替は引き続き月次画面からのみ実行し、切替の確定後に4画面が新しい店舗を参照します。成功・失敗にかかわらず通常の保存先に書き戻しません。公開起動、他の画面、クリア、自動天気取得、店舗の追加・変更・削除はこの試験の対象外です。

統合試験の月次期間変更は登録済みの年度に限定します。未登録年度の登録確認・書込みに入る前に止めます。同じ年月を選び直す場合は再描画せず、未保存入力を維持します。

## 通常保存と手動復旧の接続設計案

この案は最新 `main`（`0767c081`）を基準とします。移行試験で照合するビルドは `20261121-sale-scroll20-build-113`、機能一覧の署名は `f2dd343f` です。公開ローダーへの接続は後続です。復元・再開の隔離操作は末尾に記載します。

### 起動と通常保存

| 順序 | 接続点 | 確定条件 |
| --- | --- | --- |
| 1 | 通常起動と店舗切替 | 初期店舗を生成する前に保存状態を診断する。旧方式は従来の処理で起動する。新方式は排他下で試行履歴・採用記録・元原文・確定版を照合し、IndexedDBから読み取った内容を初期化に渡す。読めない場合は保存を停止する。 |
| 2 | 今日の入力、売上・客数・廃棄、時間帯客数、販売数 | 画面を開いたときの店舗・日付・版を保持し、入力内容と同じ操作で更新する天気・気温・メモを確定候補へ含める。確定版を読み戻してから画面に反映し、入力を消す。 |
| 3 | 店舗・年度・カテゴリー、日／月クリア、CSV、イベント、設定、天気 | 同じ保存処理へ段階的に接続する。確認ダイアログやファイル読み込みをまたぐ場合は、確定直前に対象と版を照合する。店舗削除と次の店舗選択など、複数の変更は一緒に確定する。端末固有の表示設定は既存の保存仕様を維持する。 |
| 4 | 暗号化バックアップと復元 | バックアップは読戻し済みの確定版を使う。復元は現行ファイル形式と整合性検査を維持し、復元候補を前の版と区別して保存する。後続版があるときは巻き戻さず保存を停止する。復元成功の表示は確定結果を検証した後に行う。 |

通常保存は、既存の同期 `InsightStorage.writeSnapshot()` と `transaction()` の呼出元ごとに、IndexedDBの非同期確定を待てるようにする。旧方式の呼出契約は維持する。新方式の操作は、画面に表示した版に対して `save(expectedRevision, snapshot)` を実行する。版不一致、書込み中断、読戻し失敗では入力を画面に残し、成功表示を出さない。結果が不明な場合は追加保存を停止し、自動再試行や旧保存先への書き戻しを行わない。隔離実装の最初は起動と一つの明示保存をつなぎ、上の表と既存一覧で全入口の接続を確認してから切替を検討する。

### 手動復旧

| 状態 | 復旧画面の扱い |
| --- | --- |
| 旧保存先とIndexedDBの内容が競合 | 旧保存先の編集、IndexedDBの確定版と直前版を保持する。確認できる店舗・年度・版を表示し、双方の原文から暗号化した控えを作成して検証する案を採る。両方を保全できない場合は保留を継続する。 |
| 保存中断・復元結果不明 | 採用記録と操作ID、現在版、直前版を照合し、確定を確認できる候補を示す。候補が有効でも利用者が確認するまでは保存停止を継続する。 |
| データ欠落や照合不能 | 保存停止を維持し、暗号化バックアップの復号・整合性検査・内容確認へ案内する。残っているデータと記録を保持する。 |

控えの検証後に再開を選ぶ場合は、選択前に表示した版、採用記録、旧保存先の原文を排他下で再照合し、変更があれば停止を継続する。競合時にどちらの版を使うかと、両方にしかない編集をどう扱うかは利用者の判断が必要になる。日時や版番号での自動採用、自動合成は行わない。旧版からの書込みを排除できない状態では、読み取りと控えの保全までとする。

接続ごとに架空の2店舗・複数年度で、保存直前の別タブ編集、書込み中断、読戻し失敗、復元確認中の版変更をChromiumとWebKitで検証する。今回の工程はiPad実機テストを省略し、完全オフライン時のWebKitのPWA起動は未検証と記録する。

### 最初の保存入口の隔離試作

採用済みの起動分岐で、旧シェルを開かずにIndexedDBの確定版を読み、架空の売上入力画面を表示します。対象は起動時の店舗と試験で指定した年度・月・日で、既にある1日分の売上のみを変更します。保存中は確定済みの額を維持し、取引の読戻しと採用記録の確認が済んでから画面を更新します。結果が不明な場合は入力値を画面に残し、追加保存を停止します。試験では別店舗・別年度・同じ行の客数や天気、旧保存原文が変化しないことも照合します。同じ手順を既存の売上画面に接続する作業と、その他の保存入口、手動復旧、本番の起動分岐は後続です。

### 既存の売上入力画面の隔離接続

隔離試験で既存の売上入力画面を開き、既存の保存ボタンをIndexedDBへつなぎます。試験範囲は接続時に表示していた1日分の売上（千円）と買上点数です。同期の保存処理はこの接続を読み込んだ場合にのみ抑止し、天気の共有、他の日付、ほかの保存入口はこの接続に含めません。開始時の対象と確定データを照合し、処理中は画面操作を止めます。確定結果の読戻し後も対象を照合し、既存の保存成功表示を出します。版の競合や結果不明時は入力を残して追加保存を停止します。非同期の操作監視や未保存状態の統合は、通常の保存経路を接続する工程で扱います。

### 売上の月次保存と共有天気の隔離試作

既存の売上画面で、同じ月の複数日の売上・買上点数を編集できます。売上画面の天気表示は参照専用です。共有天気への連動試験では架空の天気変更を下書きに入れ、既存の保存ボタンで対象月の入力とまとめて1版に確定します。天気は該当日がある各店舗にも反映し、各店舗の売上・客数・メモなどの値を保持します。確定読戻しまで画面の保存成功を表示しません。試作の状態確認は未保存入力と処理中・停止を区別します。既存の同期監視との接続、画面遷移時の未保存警告、他画面の保存、手動復旧は後続です。

### 売上の保存状態と移動時の警告

隔離試作で売上を保存すると、既存の操作監視はIndexedDBの結果が返るまで処理中を維持します。読戻し済みの値が画面の下書きと一致すると未保存状態が解除されます。変更なしで保存を押した場合は新しい版を作りません。結果不明や保存失敗は停止として扱い、入力を画面に残します。売上画面から別の画面に移動する場合や、売上の日付選択で月をまたぐ場合は未保存入力を警告し、取消時はその場に残ります。処理中・停止中はこれらの移動を抑止します。運用全体への接続、店舗切替、他画面の保存、ブラウザータブを閉じる場合の挙動は別途検証します。

### 未保存の画面移動経路の統一

隔離試作の売上画面で、サイドバーと直接の画面移動を同じ確認条件にし、月の移動は日付選択と期間切替から共通の確認を通します。サイドバーでの承認は、同じクリックによる画面移動に一度だけ適用します。取消時は入力と期間を保持し、承認して移動した場合は対象月の下書きを破棄します。再入場時は確定データを表示し、元の試験対象月で保存を再開できます。別の月では試験用の売上保存を受け付けません。店舗切替とブラウザー終了は別工程です。

試験保存の対象外の月でも、売上・買上点数・天気の下書きを、その月の確定済みデータと比較します。比較できない場合は未保存として扱います。保存ボタンで対象外と表示した後も未保存状態を保ち、画面移動・月の切替で取消を選べば入力を残します。明示的に移動を承認したときだけ下書きを破棄します。

### 客数・廃棄の月次保存

隔離試験の月次アダプターを、売上・客数・廃棄のいずれか一画面へ接続できます。客数は対象月の客数のみ、廃棄は対象月の変更した内訳とその日計を保存します。内訳に追加情報があれば保持します。同じ操作監視と未保存警告を使い、保存結果の照合後に成功を表示します。通常起動、同じタブで複数の月次画面を接続したまま切り替える操作、他の保存入口への接続は後続です。

### 同じタブでの月次画面切替

隔離試験で売上・客数・廃棄を切り替えると、最初に開いた各画面の店舗・年度・月を保存対象として記録します。全画面で確定済みのスナップショットと版を共有し、直前の画面の確定結果を次の画面が使います。保存中および結果不明時の停止も共有します。未保存入力を持つ画面からの移動の取消、処理中の移動と別の保存の拒否、元の画面への再入場を隔離環境で検証します。本番の画面接続、店舗切替とタブ終了時の保護は後続です。

### 店舗切替の隔離試作

同じタブで3画面を接続する隔離試験では、月次入力画面の店舗セレクターから明示確認を経て店舗を切り替えます。取り消すと表示店舗と下書きを保持します。承認後も、IndexedDBで選択店舗と共有天気を保存し、確定版を読み戻すまで表示店舗を維持し、追加の保存・切替・移動を止めます。確定後に下書きを破棄し、新しい店舗の確定済みデータを表示して各画面の保存対象を登録し直します。競合や結果不明時は追加保存を停止します。店舗の追加・変更・削除、月次入力画面外の切替、本番の起動接続は対象外です。

### 店舗・年度管理の現行経路と隔離接続の設計

| 操作 | 現行の保存入口 | 隔離接続時の確定範囲 |
| --- | --- | --- |
| 店舗追加・名称変更・削除 | 店舗メニュー。名称変更は現在のIDで `persist()`。追加と削除は `persist()` 後に `switchStore()` が再保存する。削除は店舗名を示す確認があり、2店以上で表示する。 | 名称変更では店名だけを更新して既存IDを維持。追加では新しいID・当年の行・選択店舗を1版に確定。削除では削除対象のIDと次の選択店舗を確認時に固定し、対象店舗の削除と選択切替を1版に確定。他店のデータと共通マスターを保持し、切替先の天気が空欄の場合は共通天気で補完する。 |
| 年度追加 | 設定「年度管理」の追加欄と、今日の入力・売上／客数／廃棄・販売数入力の未登録年度への移動。現行は `InsightYearManager.promoteCurrent()` から同期保存する。 | `InsightYearManager.promote()` を候補スナップショットに適用する。未登録年度の既存行を保全し、足りない行を補完する。日付、年月、描画は確定後に移動する。 |
| 年度削除 | 設定「年度管理」の選択ダイアログ。`InsightYearManager.removeCurrent()` で保存し、その後に基準年・比較年・各入力画面の期間を再調整する。最後の1年度は削除できない。 | `InsightYearManager.removeYear()` を候補に適用して、対象店舗・年度の実績、月次補助、納品・販売・廃棄数、時間帯別客数だけを削除する。他店・共通天気、対象店舗のイベント記録・設定は保持する。対象の店IDと年を確認時に固定し、確定後に既存の選択補正を行う。 |

試験接続では、確認の取消時に保存せず、対象のIDと表示・下書きが確認中に変化した場合は保存を停止する。保存前から操作を排他し、確定版の読戻しまで選択店舗・年度・ダイアログを維持する。容量不足で確定できない場合は元版を保ち、書込み後に応答を受け取れない場合は確定版・直前版を照合して復旧を判断する。ここでは架空の削除候補と保存層の保護を検証する。画面の確認・取消、選択店舗や年度の再描画、復元操作は実際の隔離接続時に検証する。

共通の隔離入力セッションで店舗・年度管理を明示的に有効にした場合、店舗メニューの追加・名称変更・削除、設定の年度追加・削除、今日の入力・月次入力・販売数入力からの未登録年度への移動に接続する。店舗メニューは今日の入力、月次入力、設定で試験する。追加・削除の画面は既存の確認操作を使用し、保存結果を読み戻してから店舗名・期間・下書きを再描画する。

### CSV取り込みの隔離接続

試験用の設定画面からCSVを選択し、読み込み開始時の店舗・保存版・画面状態を確認後と読戻し後にも照合する。確認画面は取込先店舗、対象年度、取り込む行数、対象外の行数、重複日付の件数を表示する。同じ項目には後の行の正の値を適用し、空欄や0で既存値を消さない。新年度の登録では復元できる既存行を保持し、対象外の店舗・日・項目を残したまま一度に確定する。未対応の引用符・列数や不正数値を検知すると取り込みを止める。取消や全データが一致する場合は版を追加しない。復元は別工程で扱う。

試験用の数値検証は、正の符号付き数値を受け入れ、負数や安全な整数の範囲を超える値を取込前に拒否する。廃棄内訳は各列を確認してから合算し、内訳小計と最終的な廃棄金額の範囲も照合する。

### イベント・催事・セールの隔離接続

「今日の入力」の登録・編集・削除、共通の「よく使うセール／イベント／催事」、特需商品カテゴリーの編集を、既存のイベント候補作成と検証を通して共有版へ保存する。開催記録の適用範囲、開催期間、編集時のID、プリセット参照を保持する。確認前から店舗・日付・ダイアログの入力状態を照合し、確定版を読み戻した後に一覧を更新する。結果不明時は入力を表示したまま追加の保存を停止する。

### 設定・天気の保存経路

| 操作 | 保存先・接続状況 |
| --- | --- |
| ライト／ダーク | 端末の `insight_dark`。既存の切替を試験セッションでも使い、業務データの版を増やさない。 |
| 手動の天気・最高／最低気温 | 既存の試験用日次保存に含まれる。天気は共有天気と同じ日を持つ店舗、気温は地点が一致する店舗と対象日を照合して確定する。 |
| 「自動」の取得 | 管理試験セッションの「自動」を押したときだけAPIを呼び、日次入力の下書きを補完する。店舗・対象日への移動・確定版・手動の天気または気温入力が変わった場合は応答を破棄する。保存は従来どおり日次画面の保存ボタンから行う。 |
| 店舗の天気地点 | 検索の開始時と選択時に対象店舗・画面・確定版を照合する。設定・解除は明示確認後に対象店舗の地点だけを1版に保存する。他店の地点・既存気象行・共有天気は保持し、読み戻し前には成功を表示しない。 |
| 過去の天気の一括取得 | 試験セッションの設定画面から、店舗・期間ごとに欠損値だけを1版で確定する。既存の地点別の保存範囲と共有天気を維持する。 |

隔離の採用済み起動では、未来日の日別天気・最高／最低気温と共有天気を候補版から除く。変更があるときのみ読み戻しまで1版に確定し、結果が不明な場合は入力画面を開かない。

区間の開始時に確定版から対象店舗・地点・日付を取得し、応答後に画面と確定版を再照合します。中止は未確定の取得を破棄し、再開時に確定版から欠損を計算し直します。別タブ競合や確定結果不明の場合は追加保存を止めます。通常モードには既存の一括取得経路を使用します。

### 暗号化バックアップからの隔離復元と保存再開

- 復元の対象は、現在版・旧原文・採用記録を照合できる採用済み環境です。選んだ暗号化ファイルを復号して既存の形式・店舗・年度・整合性検査を通し、現在の確定版と一致する別の暗号化バックアップを照合します。確認を得てから両方の版に変更がないことを再照合し、復元候補を次の版に保存します。復元前の確定版は直前版として保持します。さらに古い直前版は通常保存と同様に置き換わります。
- 採用中断や保存・復元の結果不明から再開するときは、現在版と採用記録を照合し、その版と一致する暗号化バックアップを確認します。利用者の明示確認後、確定版・直前版・採用記録・旧原文を再照合してから採用記録を有効に戻します。確定済みの結果を巻き戻したり、読み戻せない候補を再適用したりしません。
- 旧版を終了した旨の確認、オンラインの最新ビルド照合、Service Workerの状態確認が両操作に必要です。旧原文の競合、保存領域の欠落、証拠の不一致では書き込みを再開しません。暗号化書き出しでは、確定版を読み、既存形式で暗号化し、ダウンロード直前に同じ版を読み直します。復元・再開の成功後は、画面を再起動するまで確認フォームを無効のままにします。採用記録がない環境の復旧は従来どおり内容確認までです。

### 試験接続と公開前の確認

| 接続先 | 試験での保存範囲 |
| --- | --- |
| 人件費・粗利率 | ダッシュボードで選択した店舗・年度・月の一項目。閲覧時は初期値を保存領域に生成しない。 |
| 廃棄予算 | 廃棄画面で選択中の店舗の予算項目。確定版を読み戻すまで編集画面を保持する。 |
| 暗号化書き出し・復元・再開 | 隔離フォームで使用する。成功時は隔離ホストが確定版を読み直す。隔離ローダーから開いた設定画面では既存のバックアップ・復元ボタンを隔離処理に接続する。検証済みの中断状態では起動の停止画面から再開を案内する。 |
| 起動時の未来日気象補正 | 隔離ローダーが確定版を見て、未来日の気象項目と共有天気だけを補正してから採用済み画面を開く。今日・過去日、売上などの他項目、旧原文はそのまま保持する。 |

公開ローダーの接続前には、通常設定画面の書き出し・復旧経路と、各保存入口の再読込時の確定版表示を確認する。旧版との競合や保存領域欠落で双方の版を照合できない場合は、書き直しを停止する。完全オフラインのWebKitでホーム画面から旧PWAを再起動する実機経路は未検証。


### 公開切替の確認順序

1. 保存入口を一覧と照合する。日次・月次・販売数・時間帯別客数・イベント・セール・管理・CSV・天気・設定・バックアップを同じ保存版で確認する。設定画面のバックアップ／復元入口の配線は隔離ホストで検証する。
2. 旧版を閉じ、オンラインでビルドと機能構成を確認する。旧データを暗号化し、復号して対象店舗・年度・原文との一致を確認する。検証済みの元ファイルを保存してから、試行記録・採用記録を順に確定する。
3. 採用後は確定版と採用記録を照合してから画面を開く。隔離設定画面で復元した場合は、以前の画面を操作不能にして採用済み起動から読み直す。再開画面は中断の検証結果が一致する場合に表示する。
4. 旧版の編集、採用記録の欠落・破損、履歴またはDBの欠落を確認したら、残る旧原文・確定版・直前版を保全する。両方の版を照合できない状態ではロールバックや再移行を実行せず、編集を停止する。採用の証拠がすべて失われて旧原文だけが残った場合は、未移行の状態との識別ができないため、公開切替の判断に残す。
5. オリジンを停止して旧キャッシュからブラウザーを開く自動試験は、通信が届かない状態で旧画面が残ることと、新しい起動が異なる旧原文を見て停止することを検証する。iPadホーム画面のWebKit実機と、端末の全ストレージ消失時に最後の確定版を復元できるかは未検証。実際の公開ローダー接続と採用開始には別途承認が必要。

| 操作 | 試験で確認する保存先・範囲 |
| --- | --- |
| 今日の入力・日次クリア | 選択店舗・日付。売上、客数、買上点数、廃棄、店舗メモと関連する共有値。 |
| 月次売上・客数・廃棄、客数月次クリア | 選択店舗・年月の対象列。対象外の列・日・店舗と直前版を保持。 |
| 時間帯別客数、販売数、カテゴリー | 時間帯別の入力／全消去と、販売数・便・廃棄数・カテゴリー設定を共有の確定版で照合。 |
| イベント・催事・セール | 店舗と共有範囲、期間、既存ID、登録／削除、テンプレート。 |
| 天気・気温・地点・一括取得 | 選択日と地点、他店舗との共有範囲。有効な応答だけ確定し、起動時補正は未来日だけを対象にする。 |

| バックアップ・復元・再開 | 初回移行は保存した暗号化ファイルを選び直し、復号内容を照合する。採用後は確定版から書き出し、復元時の安全用ファイルを照合してから次の版を保存する。 |
| 全画面・起動 | 試験UIで対象外の保存を止める。公開ローダーへの接続と、ホーム画面からの起動は公開判定の対象に残る。 |

### 復旧と停止の判定

| 状況 | 保存・復旧の扱い |
| --- | --- |
| 移行前で、旧原文と保存済み暗号化バックアップが一致 | 旧版の終了と起動環境の条件も満たしたら、隔離の移行画面で明示的に移行できる。ファイル未選択、復号失敗、内容不一致なら試行・採用記録を作らない。 |
| 採用記録・確定版・直前版を確認できる | 確定版を書き出せる。復元は現在版と一致する安全用ファイルと復元対象ファイルで確認し、現在版を直前版として残す。 |
| 中断を記録し、書込前後のどちらかを検証できる | 一致する暗号化バックアップと明示確認がそろった場合だけ再開する。 |
| 旧キャッシュや別タブが旧原文を変更 | 残存する旧原文・確定版・直前版を保全し、編集・自動復旧を停止する。片方で上書きしない。 |
| 採用記録、履歴、保存DBの一部が破損・欠落 | 編集を停止し、残る記録と外部バックアップを確認する。確定版を証明できなければ自動で再移行しない。 |
| 採用に関する証拠がすべて消失し旧原文だけが残る、または端末の保存領域が全消失 | ブラウザー内の記録から最後の確定版を証明できない。端末外の暗号化ファイルと照合した手動復旧が必要。自動採用や旧原文への巻き戻しを公開手順に含めない。暗号化ファイルがなければ本番切替を保留する。 |

ファイルの見た目やダウンロード成功表示だけで判定せず、開き直しと復号を確認する。実端末の保存領域が失われた場合に備え、移行元・復元前の安全用ファイルに加え、移行後も確定版の暗号化バックアップを端末外に保管する。ホーム画面から開くiPad実機での完全オフライン動作は未検証。公開ローダーへの反映と本番データの切替は承認後の別工程とする。
